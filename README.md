# Procurement AI Agent — PoC

Прототип аналитического ассистента для работы с данными государственных закупок Казахстана. Система загружает сведения из OWS GraphQL API, хранит их в PostgreSQL, выявляет статистические отклонения цен и объёмов и отвечает на вопросы на русском и казахском языках.

> **Статус:** proof of concept (PoC), не промышленная система и не инструмент установления нарушений. Выявленные отклонения — сигналы для дальнейшей экспертной проверки.

## Возможности

- Поиск договора по ID: номер, финансовый год, БИН заказчика и поставщика, сумма, число позиций.
- Поиск потенциальных **ценовых аномалий**: отклонение цены позиции более чем на 30% от средневзвешенного ориентира по ЕНСТРУ и единице измерения; при достаточной выборке учитывается сезон подписания договора.
- Объяснение ценового сигнала с идентификаторами позиции и договора, ценой, ориентиром, процентом отклонения и числом сопоставляемых позиций.
- Поиск **аномалий объёма**: количество более чем втрое превышает медианное по ЕНСТРУ и единице измерения.
- Маршрутизация запросов на русском и казахском языках через локальную LLM (Ollama / `llama3.2:3b`). Факты и вычисления поступают из SQL, а не генерируются моделью.
- Контейнерный запуск агента и PostgreSQL через Docker Compose.
- Скрипт последовательного обновления данных и настроенное локальное ежедневное расписание Windows.

## Стек

Python 3.10, PostgreSQL 16, psycopg 3, requests, OWS v3 GraphQL API, Ollama (`llama3.2:3b`), Docker / Docker Compose. Архитектура допускает последующий перенос в Kubernetes; кластер и манифесты в рамках текущего PoC не развёрнуты.

## Быстрый запуск

### Требования

- Docker Desktop и Docker Compose;
- работающий Ollama на хосте с моделью `llama3.2:3b`;
- файл `.env` с настройками подключения и токеном API (не публиковать в репозитории).

Пример переменных окружения (значения заменить собственными):

```dotenv
POSTGRES_PASSWORD=CHANGE_ME
DATABASE_URL=postgresql://procurement:CHANGE_ME@localhost:5432/procurement
OLLAMA_URL=http://localhost:11434/api/chat
# Токен OWS API: имя переменной должно совпадать с тем, которое читает goszakup_client.py
```

> Для контейнера `agent` адреса БД и Ollama переопределяются в `docker-compose.yml`. Адрес `host.docker.internal` рассчитан на Docker Desktop. Сам `.env` не включайте в Docker-образ и систему контроля версий.

Запуск PostgreSQL:

```powershell
docker compose up -d postgres
```

Запуск интерактивного агента в отдельном контейнере:

```powershell
docker compose run --rm --no-deps agent
```

В интерактивном режиме можно задавать вопросы о договорах, ценовых отклонениях и объёмах. Для выхода: `exit`.

> Команда `--no-deps` предполагает, что PostgreSQL уже запущен и база заполнена. Docker Compose **не загружает данные автоматически**. Если контейнеры ещё не собраны после изменения исходников, предварительно выполните `docker compose build agent`.

### Запуск из Python

При запущенных PostgreSQL и Ollama и настроенном `.env`:

```powershell
python llm_agent.py
```

## Загрузка и обновление данных

ETL состоит из четырёх последовательных этапов:

1. `main.py` — получение договоров по БИН и годам из OWS GraphQL API;
2. `import_contracts.py` — загрузка договоров и позиций в PostgreSQL;
3. `fetch_plans.py` — получение связанных планов закупок;
4. `import_plans.py` — загрузка планов в PostgreSQL.

Оркестратор `refresh_data.py` запускает эти этапы последовательно, включает `REFRESH_CONTRACTS=1` и `REFRESH_PLANS=1`, останавливается при ошибке дочернего процесса. Файлы выгрузки сохраняются локально в `data/raw/`.

```powershell
python refresh_data.py
```

**Осторожно:** эта команда запускает полное обновление и может потребовать значительного времени и сетевых запросов. В текущем окружении ежедневное расписание настроено через Windows Task Scheduler, но успешное выполнение полного цикла по расписанию пока не подтверждено. Для непрерывного SLA обновления в течение 24 часов потребуется постоянно доступная среда выполнения, журналирование и контроль ошибок.

## Методика анализа

### Ценовые отклонения

Сравнение проводится внутри сочетания **ЕНСТРУ + единица измерения**. Используются последние версии договоров в цепочке `root_id`, положительные цены и количества, неудалённые позиции и арифметически согласованные записи (`|цена × количество − сумма|` в пределах допуска).

Для сезонного сравнения применяется сезон **даты подписания договора**: зима (декабрь–февраль), весна (март–май), лето (июнь–август), осень (сентябрь–ноябрь). Если после исключения собственного договора доступно не менее 10 сопоставляемых позиций того же сезона, используется сезонная средневзвешенная цена; иначе — глобальная по тому же ЕНСТРУ и единице измерения. Сигнал формируется при превышении ориентира более чем на 30%. В демонстрационной выборке применяется дополнительный верхний фильтр `цена < 3 × ориентир` — это ограничение выдачи, **не** универсальное правило выявления аномалий.

`fair_price_seasonal_v1` также содержит медианный бенчмарк (с минимум пятью разными договорами в группе). **Медиана в представлении и средневзвешенный ориентир в функции поиска аномалий — разные показатели.** Показатели покрытия сезонного представления не следует трактовать как покрытие фактической выдачи агента.

### Аномалии объёма

По ЕНСТРУ и единице измерения вычисляется медианное количество (минимум 10 позиций и 5 разных договоров). Сигнал формируется, когда количество конкретной позиции более чем в три раза выше медианы. Отличие потребностей заказчиков и технических характеристик не исключается.

### Достоверность

Аномалия — **статистический сигнал**, а не доказательство завышения цены, коррупции или нарушения законодательства. Одинаковый ЕНСТРУ не гарантирует одинаковую комплектацию, качество, характеристики и условия поставки.

## Результаты внутренней оценки

| Проверка | Результат | Область применимости |
|---|---:|---|
| Маршрутизация намерений RU/KZ | 47/50 = **94%** | 50 размеченных вопросов, 5 категорий |
| Проверка полей ответов о договорах | 35/35 | 5 договоров × 7 полей; ограниченная выборка |
| Проверка фактов в SQL | 35/35 | 5 договоров × 7 проверок |

Эти результаты **не доказывают 85% точности всех ответов**. Для общей оценки необходимы согласованные критерии, репрезентативный набор вопросов и эталонные ответы, включая неоднозначные товары и корректные отказы от необоснованных выводов.

## Известные ограничения

- **Региональная корректировка не реализована:** в текущих выгрузках договоров и планов нет подтверждённого региона фактической поставки. Архитектурно возможно добавить региональную группировку при наличии данных. БИН или юридический адрес заказчика не считаются эквивалентом региона поставки.
- Сезон определяется **датой подписания**, а не датой фактической поставки; одинаковые сезоны разных лет объединяются без отдельной инфляционной поправки.
- Бенчмарки не гарантируют сопоставимость спецификаций товаров; нет внешней верификации рыночных цен.
- Поиск аномалий использует фильтры и пороги PoC; отсутствие сигнала не означает отсутствие нарушения.
- Часть планов недоступна; качество и полнота зависят от OWS API.
- Обновление по расписанию настроено локально, но полный end-to-end refresh ещё не подтверждён; компьютер должен быть доступен.
- Промышленная инфраструктура (Kubernetes, мониторинг, централизованное управление секретами, отказоустойчивость) не развёрнута.
